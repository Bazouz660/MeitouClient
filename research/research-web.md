# Multiplayer research brief (web)

Conventions: every claim has a URL. "[memory]" = from my background knowledge, not confirmed in this session. Many search results were summaries by the search tool, not the full pages. Where only a summary supports a claim I say so. Several primary pages (Nexus, Fandom, Unreal Iris docs, Source wiki, Wolfire) returned 403/402/404, and the Steam Workshop page returned 429 on every retry.

## 1. Existing Kenshi multiplayer projects

### "Anarchy" = Steam Workshop item 3808257125, title "Kenshi Multiplayer" (module name AnarchyKenshi), author "Anarchy"
- Could NOT read the Workshop page (HTTP 429 three times). Nexus page https://www.nexusmods.com/kenshi/mods/2183 returned 403. What follows is from search-result summaries of those pages plus titles, so it is thin and from the author's own marketing.
- Scale: "Whole of Kenshi's open world, shared by up to 200 players on one server", persistent dedicated server (Nexus summary: https://www.nexusmods.com/kenshi/mods/2183). A YouTube video is titled "Check Out the 500 Player Kenshi Multiplayer Mod by Anarchy!" (https://www.youtube.com/watch?v=zDfkg4BK3Dc). The title is all I could read, no description, so 200 vs 500 is unresolved (could be a different build or server).
- Server: described as a persistent dedicated server; the client lists servers under MULTIPLAYER and you create an account name and password (summary of https://steamcommunity.com/sharedfiles/filedetails/?id=3808257125). The summary says the client shows the server's zones, NPCs and server frame rate beside ping, and that a stalled server physics loop warns everyone and restarts itself 2 minutes later. This suggests the server runs the world itself (zones, NPCs, physics) and is authoritative. Whether it is headless, whether it embeds a Kenshi/engine instance, and its tick rate: NOT confirmed.
- Factions and economy (summary only): players carry materials to a faction's build site, the server takes them from the character's bag and puts them in the site so all see one count; trading goes through the server. This implies server-owned inventories and buildings. Faction joining, diplomacy: NOT confirmed.
- Install: copy folder to Kenshi mods, run an enable batch file, tick it in the launcher's MODS tab (same sources). So it runs as a data/launcher mod plus native injection; details unknown.
- Versions: Workshop change notes show 78 entries titled "Update" by Anarchy from 30 Oct to 3 Nov; client/server 0.91.11, later protocol 92 that drops older clients (https://steamcommunity.com/sharedfiles/filedetails/changelog/3808257125). Entries have no text on page 1.
- Status: a search summary of the changelog page said the Workshop item "has been removed"; that is contradicted by Steam's own API, which on 18 November 2026 returned the item as public and not banned (title "Kenshi Multiplayer", updated 4 November). Treat it as live. See `anarchy-notes.md` for what the author says about how it works.
- NOT confirmed at all: interest management, who owns NPCs on a technical level, time/pause, saves, mod support, commenter-reported problems, whether it is client-hooked or a reimplementation. The Discord is where this would be found.

### Kenshi-Online / KenshiMP (The404Studios)
- Repo: https://github.com/The404Studios/Kenshi-Online (README, read). 16-player co-op (`maxPlayers` 16 in sample server.json), alpha v0.3.0. ENet with 3 channels; client `KenshiMP.Core.dll` injected in Kenshi with 14 hook modules (entity, combat, time, movement...), dedicated `KenshiMP.Server.exe` (NetServer, AuthValidator, GameState, WorldPersistence), master server on port 27801 for a server browser, default game port 27800.
- Authority: README says "Server owns truth, clients own input", server validates all commands, generation tracking against ghost control. Client prediction reconciliation is a stub.
- Known issues listed by the README: "AI not synchronized (local AI decisions)"; combat damage bars do not sync (ApplyDamage hook crash).
- A search-tool summary claimed "server owns NPCs, 3x3 zone grid around each player, each player owns their squad" (search result for https://github.com/The404Studios/Kenshi-Online), but the README text I fetched does not state it and also says AI is not synchronized. Treat the zone grid claim as unconfirmed. Time/pause, saves format, mods: not described (clients "load your save" first).
- Hosting guide by a hosting company: https://client.citadelservers.com/knowledgebase/1312/Kenshi-Online-Multiplayer-Installation-and-Setup-Guide-for-Players-Joining-a-Server.html (marketing-ish).

### KenshiCoop (nhoral)
- https://github.com/nhoral/KenshiCoop (README, read). RE_Kenshi/KenshiLib plugin, Kenshi 1.0.65. ENet over UDP with an optional Steam P2P tunnel (no port forwarding); players paste each other's Steam IDs per session. AGPL-3.0.
- Authority: "The host is authoritative for the world; each client is authoritative for its own squad." Each player controls one squad; a friend's squad is synced to you and answers only to its owner.
- Replicates squads, NPCs, combat, inventory/equipment, trades, ground drops, base building, container contents, a shared money pool (Kenshi has one wallet), and game speed. Pause handling not described.
- Saves: any save by either player becomes one shared save streamed to both; the host streams its world on connect, joiner uses an identical on-disk copy if present.
- Limits: 2 players is the design target; "Expect rough edges, desyncs, and crashes"; both must run the same build ("protocol mismatch"); a one-squad save needs units moved to a second squad by hand.
- Lesson common to both: they bolt multiplayer onto a single-player engine that was not built for it (hooks, local AI), and report desync, crashes and AI that is not synchronized. Your headless simulation avoids that class.

## 2. Syncing a big world for many players (server-authoritative)

- Priority accumulator with a byte budget: each object has a persistent priority accumulator, added every frame; sort by accumulator, fill the packet until the byte budget (example 256 kbit/s) is used, reset the accumulator only for objects sent; budget can be changed live; fixed raising of important objects, otherwise resting objects starve (https://gafferongames.com/post/state_synchronization/).
- Delta compression: encode a snapshot relative to a baseline the receiver has acknowledged; one bit "unchanged" per object gives the biggest early saving; baseline trails by about one RTT (https://gafferongames.com/post/snapshot_compression/).
- Unreal Replication Graph: built for 100 players and about 50,000 replicated actors (Fortnite BR); per-actor-per-client relevancy checks "bottleneck the server's CPU"; instead, persistent nodes hold lists, a spatial grid gives each client the precomputed actor list of the cell around it, dormant actors (rarely changing) send only on change, per-connection/team always-relevant lists, carried items replicate with their owner (https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine). Iris docs unreadable (403); [memory] Iris adds filtering and prioritization groups and delta compression.
- Halo: Reach / Tribes model: unreliable, unordered replication of object properties, objects sorted by a per-client priority (summarised in a Warframe deck: https://www.slideshare.net/slideshow/networking-architecture-of-warframe/76337882 and https://edgegap.com/blog/game-backend-deep-dive-halo-reach-netcode-host-migration). Secondary summary says four of five major bandwidth wins in Reach came from game-design changes (https://www.jikguard.com/news/video-networking-the-online-gameplay-of-halo-reach). The Bungie bandwidth figures (250 kbit/s host minimum, 675 max) are unverified. Primary slides not read.
- Overwatch (Ford, GDC 2017): prediction plus reconciliation, small netcode surface in an ECS (https://gdcvault.com/play/1024001; details from third-party write-up https://edgegap.com/blog/game-backend-deep-dive-overwatch-2016-netcode-architecture-rollback). Not very relevant to a slow squad game.
- Source engine: delta snapshots against acked ticks, PVS relevance, per-client update rate: [memory]; the wiki page returned 403 (https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking).
- Valheim shows the cost of not doing deltas: a changed ZDO is resent whole, active ZDO volume grows with player count, hard-coded rate limits, slowdown near 5-6 players, cap of 10 (https://edgegap.com/blog/valheim-multiplayer-game-backend-deep-dive).
- Cells with hysteresis: Improbable's patents describe overlapping authority bands "to prevent authority thrashing (e.g., spatial hysteresis)" and interest regions that shrink as load rises (https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10878146 and the family listed in the search). These are patents, not product docs.

## 3. Simulating only where players are

- Minecraft: simulation distance (entities ticked in a square of side min(2s+1,63) chunks around each player ticket; default 10 in Java multiplayer) is separate from view distance (what the client draws); a one-chunk frame beyond still ticks blocks; beyond that "nothing moves or changes" (https://minecraft.wiki/w/Simulation_distance, https://minecraft.wiki/w/Chunk). Ticket levels: entity ticking <=31, block ticking 32, border 33, inaccessible 34+; forced chunks, portals and pearls hold chunks too; a dimension with no keep-alive stops ticking after 300 ticks. Integrated server in single player / Open to LAN, dedicated server with `server.properties`: [memory], not fetched.
- Valheim: whichever player loads a zone first owns and simulates it and its creatures, ownership is per zone and not rebalanced; even on a dedicated server the model is largely peer-owned; a "simulation distance" launch option limits zones per owner (search summary of community mod pages, e.g. https://thunderstore.io/c/valheim/p/Terramizer/TerramizerServer/ and https://supercraft.host/wiki/valheim/better-networking; secondary). Cost: a client with ownership can cheat or lag everyone in that zone [memory-based inference].
- EVE Online: dilation is per node (not per system); systems are assigned to nodes by estimated load and reshuffled at daily downtime; reserve nodes can be booked before a planned fight; a 2012 example: a node with 4 systems held 1,300+ pilots, a normal node with 83 systems 1,350+ (https://www.engadget.com/2011/10/02/eve-evolved-time-dilation-and-the-war-on-lag/, https://www.eveonline.com/article/qd92g0). A "10% minimum" was not found in sources.
- Star Citizen: a replication layer service holds entity state; one server node has authority over any given entity; authority can move between nodes; static versus dynamic meshing; as of 2024 sources, authority transfer was still limited and rollout incomplete; current status unconfirmed (https://starcitizen.tools/Replication_layer, https://api.star-citizen.wiki/comm-links/18397, https://massivelyop.com/2026/02/06/star-citizen-cto-outlines-progress-on-server-meshing/).
- S.T.A.L.K.E.R. A-Life: characters are online or offline by distance to the player (vanilla about 150 m); offline ones keep pursuing destinations and resolving group encounters in a cheaper background pass (https://www.gamedeveloper.com/game-platforms/interview-inside-the-ai-of-i-s-t-a-l-k-e-r-i-, https://gamedeveloper.com/design/a-life-an-insight-into-ambitious-ai). STALKER 2's offline behaviour is disputed by community sources (https://steamcommunity.com/app/1643320/discussions/0/4626981579416142262/).
- X4: a high-attention mode (full precision, only near the player's sector/bubble) and a low-attention mode with reduced precision and update rate; behaviour differs between the modes (e.g. combat results) (https://www.pcgameshardware.de/X4-Foundations-Spiel-61270/Specials/Timelines-DLC-Update-Vulkan-Tech-Test-Release-1449923/3/). Bubble size sources conflict.
- Not researched in this session (no sources fetched): Rust, DayZ, Project Zomboid world model, 7 Days to Die, Space Engineers, Foxhole, BigWorld cell splitting, SpatialOS docs. Do not rely on me for these.

## 4. Offline players' characters and bases

- Rust: logging out leaves a sleeper in the world that others can kill or loot; sleeping bags are respawn points that decay when outside a tool-cupboard range (~36 h); a clan with a 6-hour offline window gets raided in it; offline raid defence is advice such as keeping someone online. Sleepers can be disabled server-side (older thread) (https://guildorder.com/games/rust/guides/base-defense-and-offline-raid, https://steamcommunity.com/app/252490/discussions/0/490125103639502412).
- ARK offline-raid protection: search returned nothing; [memory] it exists as a server rule that makes offline tribes' structures damage-resistant, unconfirmed.
- Kenshi-specific writing on offline characters: none found.

## 5. Time control

- RimWorld Multiplayer: deterministic lockstep; "async time" gives each map its own tick counter, speed and RNG so players can run at different speeds; time otherwise syncs to the colony furthest ahead; community reports of async bugs; mod mismatch is the commonest desync cause; the FAQ says it is better for "live" play (https://deepwiki.com/rwmt/Multiplayer/7.1-async-time-system, https://hackmd.io/@rimworldmultiplayer/faq, https://rimworldhub.com/post/rimworld_desyncs_lets_get_back_in_sync).
- KenshiCoop replicates game speed (above). Bannerlord co-op mods: Bannerlord Online keeps a synchronized world clock that never stops, even for combat; Warhost keeps the host on the map and moves battles to a MP server; a pause-by-vote idea was only a forum suggestion (https://sourceforge.net/app/bannerlord-online/, https://www.moddb.com/mods/bannerlord-warhost, https://steamcommunity.com/app/261550/discussions/0/595135824845104100).
- Paradox multiplayer pause/speed voting: not confirmed by a source here [memory: host-controlled or vote based].

## 6. Why lockstep does not fit

- Factorio: every client runs the same simulation and only inputs are sent; a slow peer cannot be dropped, so a latency buffer is used; a desync is a state disagreement and is fixed by redownloading the map; tiny differences (even across Windows and Linux) break determinism (https://factorio.com/blog/post/fff-76, https://wiki.factorio.com/Desynchronization, https://direct.factorio.com/blog/post/fff-415).
- RimWorld shows the same fragility with mods and async time (above). For hundreds of players, each joiner must load the whole world and the slowest player paces everyone; your engine would also need bit-exact floats, which is a given inference from the sources, not stated by them.

## 7. Hosting, joining, mods

- Steam: SteamNetworkingSockets with Steam Datagram Relay hides IPs and relays over Valve's backbone (https://partner.steamgames.com/doc/api/ISteamNetworkingSockets); NAT punch-through is tried first, relay is the fallback (third-party integration guide, https://docs.coherence.io/hosting/client-hosting/implementing-client-hosting/steam-relay). The open-source GameNetworkingSockets uses ICE for NAT traversal and does not include SDR (https://github.com/ValveSoftware/GameNetworkingSockets).
- Join Game: set the rich-presence `connect` key to enable the friends-list button; callbacks differ if the game is running or not; for lobbies `InviteUserToLobby` / `+connect_lobby <id>` launch parameter; cold-launch path needs testing (https://partner.steamgames.com/documentation/matchmaking, https://wiki.facepunch.com/steamworks/SteamFriends.OnGameRichPresenceJoinRequested, https://kb.heathen.group/steam/multiplayer/rich-presence).
- Valheim dedicated server: free via Steam tools, needs no game purchase, worlds are folders (https://edgegap.com/blog/valheim-multiplayer-game-backend-deep-dive). Its crossplay path goes through a PlayFab relay and cannot run with BepInEx mods (same page).
- Project Zomboid: `servertest.ini` has `Mods=` (internal mod IDs) and `WorkshopItems=` (Workshop IDs), semicolon-separated, dependencies first, restart needed, RCON in the same file (hosting guides, e.g. https://help.akliz.net/docs/add-mods-to-project-zomboid-servers). Whitelist: not found.
- Minecraft: Forge lists missing mods on the disconnect screen; Fabric has no mod-list handshake, only registry sync via Fabric API; common error "Failed to synchronize registry data" (https://support.aternos.org/hc/en-us/articles/11901646576541-Mismatched-mods).
- Garry's Mod, Arma: see 8. SteamCMD/RCON/whitelist for Minecraft: [memory].

## 8. Server authority and code mods

- Arma 3: `verifySignatures=2` accepts only mod files signed with a key in the server's `keys/` folder; turning it off lets players join with any mods, including cheats; server-only mods need no client copy (https://community.bistudio.com/wiki/ArmA:_Addon_Signatures, https://help.freakhosting.com/games/arma-3/enforcing-v2-signatures).
- RimWorld: any mod mismatch or non-MP-safe mod desyncs everyone (above).
- Garry's Mod: no source found; [memory] server Lua runs on the server and is downloaded to clients, trust rests on the server operator.
- General inference: a client-side code mod can only be trusted for presentation; anything that changes the simulation must run on the server.

## What this suggests for our design

1. Make the server the only owner of simulation state, never a player's machine (Valheim zone ownership gives a client authority over a zone and per-zone bandwidth; Kenshi-Online states "server owns truth"; KenshiCoop's per-client squad authority only works for two trusted friends). Validate commands, not state.
2. Use one transport and protocol for local, friend and dedicated play: an in-process or loopback server in the host's game (Minecraft's integrated server [memory]), SteamNetworkingSockets with relay for friends, plain sockets for dedicated; same code path means the co-op case is just a small massive server (section 7).
3. Do interest management with a spatial grid of cells, computed once per cell rather than per entity per client, with hysteresis at the borders; Replication Graph's cost argument and Improbable's authority bands (sections 2, 3).
4. Give each client a per-entity priority accumulator with a byte budget, and lower send rates with distance, so bandwidth is bounded whatever the player count (Gaffer; Halo/Tribes priority).
5. Delta-encode against baselines the client has acknowledged, with dormant entities (sleeping NPCs, buildings) sending only on change; do not resend whole objects (Gaffer, Replication Graph dormancy, Valheim's cost).
6. Separate "simulate" distance from "send" distance, as Minecraft does with simulation versus view distance and ticket levels; simulate full detail near players, and keep a one-cell ring that ticks cheaply (section 3).
7. For the rest of the world, run a coarse offline layer for squads and towns (A-Life offline pass, X4 low attention) that moves things along routes and resolves encounters in aggregate, with a defined hand-over to full simulation; both games show the offline layer will not match full-detail results exactly, so decide which outcomes must agree.
8. Plan for load shedding on a single node before thinking of splitting the world: EVE's time dilation and Valheim/Minecraft simulation-distance knobs show a server under load should lower simulation radius or tick rate, and server meshing (Star Citizen, SpatialOS) is a long, hard project that is still incomplete; keep entity ownership behind an interface so cell splitting stays possible later.
9. Decide offline-player rules as server settings: Rust-style sleepers or pull characters out of the world, and optional offline-raid protection; nobody documents a Kenshi-specific answer, so this is a design choice, not a copied one.
10. Time: keep fixed real time on shared servers (Bannerlord Online-style clock that never stops) and allow pause or speed only where one party decides (a solo or invited-friends game, by vote or host), because RimWorld's async time is built on lockstep and is the buggiest part of that mod; deterministic lockstep is ruled out (Factorio, RimWorld). For mods, accept server-only code mods freely, require a hash or signature match for anything the client also runs (Arma), and let the server decide settings and the save.
