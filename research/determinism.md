## Determinism audit: `Meitou.Simulation` and what it calls at tick time

### Summary
- The core loop is built to be deterministic. Rolls are stateless hashes, effects are committed in a sorted order, and there are tests that agree at 1, 4 and 16 threads.
- **The interactive game is not deterministic, even run twice on the same machine.** Paths, town building and navmesh loading all run on background threads, and their results enter the world when they happen to finish. Ragdolls also feed physics results back into hashed state.
- Across operating systems, a divergence has already been **observed**: 4 of the 15 golden scenarios hash differently on Linux.
- Across CPUs, I **verified** in a scratch test that some `System.Numerics` helpers give different bits when AVX2/FMA is unavailable.

### What is already sound
- **Randomness.** `Rng.Hash(seed, entity, purpose, counter)` uses SplitMix64 (`Rng.cs:58-73`) and keeps no shared state. `Rng.Key(CharacterId)` mixes the slot and generation (`Rng.cs:76`). The simulation itself has no `System.Random`, `Random.Shared`, `Guid.NewGuid`, `DateTime`, `Stopwatch` or `Environment.TickCount`; I grepped the whole of `src/Meitou.Simulation`.
- **Hashing.** No `GetHashCode` or `HashCode.Combine` in the simulation. String keys go through `Rng.StableHash` (FNV-1a, `Rng.cs:86-91`). Sorts use `StringComparer.Ordinal` (for example `Shop.cs:111`, `ItemFactory.cs:27`, `ResearchState.cs:167`).
- **Dictionaries.** `Dictionary`/`HashSet` enumerate in insertion order, whatever the hash codes are. This holds for the `ReferenceEqualityComparer` sets in `AiSystem.cs:75,243` too. This is from my knowledge of the runtime and was not tested here.
- **Effects and commands.** `EffectBuffer.Order` is a total order: (Target, Source, System, Sequence) (`Effects.cs:62-70`). `CommandQueue.TakeDue` sorts by (Tick, Sequence) (`Commands.cs:64`). `World.Defer` is allowed in serial phases only (`World.cs:240-247`).
- **Thread count.** The `WorkerPool.ForEach` contract: "the body must write only what belongs to its number: then the thread count never changes a result" (`WorkerPool.cs:5-9`). Partitions depend on `Threads*PartitionsPerThread` (`World.cs:291-298`). `DeterminismTests` and the `WildTests`/`CombatDataTests` loops check 1, 4 and 16 threads.
- **Static state.** The only mutable statics are `[ThreadStatic]` scratch lists (`AggroSystem.cs:132`, `AnimationSystem.cs:171`). The `ConcurrentDictionary` caches (`AnimationSystem.cs:129,163,490`, `ItemFactory.cs:11,18`, `Market.cs:39`, `WorldStates.cs:17`, `BodyFactory.cs:16`) hold pure functions of the data and are never enumerated.
- **JIT.** `Meitou.Game.csproj:15,17` sets `TieredPGO=false` and `TieredCompilation=false`.

### `StateHash`
- **Where it is computed:** `World.StateHash()` (`World.cs:301-318`). It hashes Seed, Tick, `Characters.Hash` (`CharacterTable.cs:404+`, every slot's generation and alive flag, then hot fields, body, inventory, orders, AI, carry, crime and lock state), squads, platoons, player, and conditionally Uniques, Fixtures, Buildings, GroundItems, Machines and Research. Then every `IStateHashed` system is added: Aggro (with the full relation matrix once changed, `AggroSystem.cs:482-490`), Combat, Arrest, Dialogue, Flee, Kidnap, Lock rounds, Campaigns and Ragdoll poses.
- **How it hashes:** `StateHasher.Add` applies `Rng.Mix` once per value, normalises negative zero (`Rng.cs:126-142`), and is order-sensitive.
- **What it leaves out:** `GameHours`, `VisitedZones`, `Saved`, path points (only `Path.Length`), names (only the length), `ItemInstance.StolenFrom` (simulation.md:978), derived caches (AI turret and seat claims, `ProvisionalRepathTick`), and display state. Desyncs in those fields show up only later, through their effects.
- **Cost:** not measured; this is my estimate. It runs serially on one thread at roughly 150–250 `Add` calls per living character. `BodyHash` allocates `stats.ToArray()` per character (`BodyHash.cs:11`). That suggests about 0.3–0.7 µs per character, so roughly 1–2 ms for a few thousand characters, plus O(factions²) once relations change. It is affordable every N ticks, not every tick at 5× speed.
- **Callers:** only tests and the duel (`GameHost.Duel.cs:119,125,180`).
- **Docs:** simulation.md:42-44 says: "`StateHash` is ordered … a diagnostic rather than gameplay work. Golden scenarios must agree at 1/4/16 threads before pins change; **pins are platform-specific**." `GoldenHashTests.cs:74` adds: "the wandering scenarios use MathF.Sin/Cos/Atan2, which come from the platform's C library and can differ in the last bit elsewhere."

### How realistic is lockstep?
- **Same OS, same CPU class: feasible, but not as the game is wired today.** These changes would be needed:
  1. Make paths and population builds deterministic: compute them synchronously, or deliver each result at a fixed tick `T+k` and stall if it is not ready.
  2. Load the navmesh only from simulation state, and publish it only at agreed tick boundaries: no Stopwatch-based `RouteZones` or 30 s unload, the `ZoneGate` answer itself becoming a deterministic input, and `RepathCommand` made deterministic too.
  3. Either remove the ragdoll write-back to `hot.Position`/`Yaw`, or make the ragdoll collision geometry synchronous.
  4. Turn the live settings toggles into commands or session constants, and derive `GameHours` from the tick.
  5. Require identical data and mods, checked at join by a hash of the data set.

  Even then, a peer whose CPU lacks AVX2 diverges through the Lerp and matrix helpers and Bepu (verified above). Requiring x86-64-v3, or replacing those helpers with explicit scalar math, would close that.
- **Windows ↔ Linux: not realistic without replacing the trig.** Divergence is already observed in 4 of the 15 golden scenarios. Fixing it means swapping about 70 `MathF` trig and `Pow` sites in the simulation, plus the navmesh slope constants, for a managed deterministic implementation (polynomial sin, cos, atan2, asin, acos and pow). Bepu's own internal math is not audited (Unknown).

  ARM64 (macOS) would also differ in `Vector<T>` width.
- **Either way, `StateHash` at a fixed cadence is the ready-made desync detector.** It is cheap enough to run every 30–60 ticks, but it has to cover the fields it now skips (path points and the others listed above).
- **Host-authoritative replication (S) avoids hazards 1–6 entirely**, because only the host simulates.
