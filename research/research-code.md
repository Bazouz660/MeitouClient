# Multiplayer research brief: what the code assumes today

Repo D:/Github/MeitouClient, master 315d26ecf. Paths are under `src/` unless noted. "(inferred)" marks my reading, not a quoted fact. Counts come from Grep and are approximate to a few percent. No multiplayer text exists anywhere in docs/ or DECISIONS.md (searched "multiplayer", "co-op", "dedicated server", "netcode").

## 1. Headless: what a running world needs and where it lives

**Simulation owns most of it.** `Meitou.Simulation` references only Core and Data (csproj). `WorldBoot.Load` (Simulation/WorldBoot.cs:115) reads levels, navmesh (`NavSystem`), ragdoll geometry, population data, rigs and animations with "no window, GPU or audio". `StandardSystems.Build(data, walkability, options)` (Simulation/StandardSystems.cs:355) is the one wiring authority (19 `StandardParts`, flags at :19-111, options at :116-223). `World` (Simulation/World.cs:139) ticks; `WorldSettings` (:78) has Seed, Threads, TickSeconds 1/30, FarTickPeriod, PublishSnapshots (can be off).

**Game owns the glue (the parts a server must re-create):**
- `WorldSession` (Game/Host/WorldSession.cs:20): the two clocks (30 Hz control tick, sim tick), `GameClock`, `InputState`, `CameraRig`, snapshot pair, tick-ahead thread `Meitou.Tick`, `ReplaceWorld` (:147), `Step` (:286). Its constructor takes a `ground` height function for the camera rig (:37). `World.GameHours`, `Daytime`, `PhysicsSpeed`, `ViewPosition`, `ShownInteriors` are inputs copied from the session before each tick (`SimulationTick`, :313-325). The `SimulationClock`/`FixedStepClock`/`GameClock` types themselves are in Simulation/Session.
- System wiring from settings: `GameSaves.BuildSystems` (Game/Host/GameSaves.cs:677-723) turns `UserConfig` and `GameplaySettings` into `StandardSystemOptions`. Tools copy this by hand (`tools/Meitou.Tools/ProbeWorld.MakeWorld`, :261).
- Navmesh zone streaming: `GameHost` "Nav streaming" region (Game/GameHost.cs:1331-1480): `UpdateNav` (:1391) asks `Population.ActiveZones` plus `Nav.Walkability.RouteZones(30 s)` (`LoadWantedZones` :1419), caches left zones 120 s / 60 zones (`DropStaleZones` :1438), sends `RepathCommand` at most once a second (`SendRepath` :1456), relabels gate codes on the pool and sends `GateRegionsCommand` (:1506-1534). `PopulationSystem.ZoneGate` is set to `Nav.Walkability.World.Contains(zone)` at five sites (GameHost.cs:686, GameSaves.cs:500, MetalGameLoop.cs:850, NewGameLaunch.cs:46,123). A zone does not count as loaded until its navmesh is live (`PopulationSystem.Accepted`, Simulation/Population/PopulationSystem.cs:625). `tools/Meitou.Tools/ProbeZoneStreamer.cs` re-implements this loop for the tool.
- Weather: `WeatherWorld` (Data/World) holds every region's schedule, but `WorldWeather.Update` (Game/Rendering/Sky/WorldWeather.cs:16) drives it from the camera position, game time and real frame times. `WeatherFeed.HostWeather` (Game/Host/WorldSync/WeatherFeed.cs:19) is the `IWeatherSource` the world reads (`World.Weather`, Simulation/World.Weather.cs:38); the local effect zones (dust, gas, burning) come from live particle units in the renderer. Tests leave `World.Weather` null: no weather acts.
- Population loading is inside Simulation (`PopulationSystem`, optional build thread via `PopulationSettings.Background`, PopulationSystem.cs:156). Only the zone gate and `FocusCommand` come from the host.
- Saving: `GameSaves` (Game/Host/GameSaves.cs): requests, autosave (:99), `PrepareBase` on a worker (:86-91), write worker (:144), `SwapInSave` (:467-549) which restores the clock (:510), weather (:513), camera and the navmesh around the leader (:521-543) on the host side. The mapping itself is Simulation/Saving.
- Clock authority: `GameClock` is held by the session, not the world; the world's own `GameHours` is only a copy.

**Ways to run without a window today:**
- `--headless` (docs/launch-options.md:133): no window or swapchain but still draws into an offscreen picture (needs Vulkan; for the agent channel). `--hidden-window` (:132) is similar. `--no-population` runs without towns (GameOptions.NoPopulation).
- Agent control channel (`--control-dir`, Game/DevTools/Agents/AgentChannel.cs:18): file protocol, `cmd` lines in, JSON lines out, polled 4x a second on the game thread, runs the console commands (`pause`, `speed`, `step`, `select`, orders, state dump). Game thread only; not a network protocol.
- `--sandbox`, `--duel`, `--battle` (launch-options.md:65-75): scripted worlds on open ground, no towns.
- **True GPU-free world:** `tools/Meitou.Tools/ProbeWorld.cs` (`meitou-tools probe`, also `mod-check`, `WarProbe`, `TreatProbe`...) loads a real save, builds the standard systems on 1 thread, optionally the real navmesh, and calls `World.RunTick()`. It never touches rendering, but the Tools project references Game (tools csproj:10). Tests do the same (22 golden scenarios use synchronous services).
- Not found: a `MeitouServer` entry point, a project split between "world host" and "client", or a way to start `GameHost` without Vulkan.

## 2. What decides which part of the world is simulated

Both the camera and the player's characters, and each is a single-area notion.
- World: 64x64 zones of 4608 units (Data/World/WorldLayout.cs:13-18).
- `PopulationSystem.RefreshLoaded` (Population/PopulationSystem.cs:564): the **camera's** 3x3 zone block around one centre zone (`FocusCommand`, :254; the centre moves only when the focus is 4147 units off the centre zone's middle, `ZoneActivation.RecentreDistance`, ZoneActivation.cs:28; linger 4 s), plus a +-340 box round **each** living `IsPlayer` character not in a `Dormant` squad (:682-692; ring +1 with Fast zone hopping; linger 6 s), plus the box round each player-faction platoon. Towns ask all zones of their coverage list (`AskTownZones` :636).
- Without a player the focus alone centres the block; with neither nothing loads (:694).
- So multiple disjoint active areas already exist for one player's spread squad (each character's box), but exactly one camera block exists. `PopulationSystem._focus` is one `Vector3?`. Discovery adds the single focus as one more viewer, clamped to 2250 of the nearest player character (`AddFocusViewer`, :454).
- Characters are active if their zone is in `World.ActiveZones`/`LoadedZones` (World.cs:487,493); towns unload with no grace (`TownUnloadGraceSeconds` 0), wild sites 60 s, roaming 10 s (docs/simulation.md:65). Unloaded squads become pinned platoons / `StoredSquad` and the off-screen tier moves them in straight lines (docs/simulation.md:405-570).
- Step rate: `World.NearRadius` (8000, set from the character renderer's draw reach, GameHost.cs:656-657) around `World.ViewPosition`, plus `PlayerNearRadius` 1500 around each player character; others step once in `FarTickPeriod` ticks (game 4, tests/headless 1) (docs/simulation.md:70-90; World.cs:562-579). A player squad the player does not lead (`Squad.Independent`) or a mod-dormant squad counts as NPCs.
- Cost figures (docs/bench.md "character flights", an **Observed** save with 5 squad members across the map): tick about 1.5 ms + 4.5 us per loaded character at rest (4.6 ms at 715 characters, 9.2 ms at 1660); 12-13 ms while the newcomers of a 3x3 block spawn; one block loads 150-500 characters. Original: "hundreds of NPCs" per loaded 3x3 (docs/engine.md:44). Off-screen step 0.03 ms a tick with 2000 extra stand-ins (simulation.md:482). Spawn of one 8-squad town 65 ms, unload 0.02 ms (simulation.md:65). Navmesh zone build time is not given in the docs I read.
- (inferred) For hundreds of players the loaded set is N x (box + camera block); nothing deduplicates cost beyond the zone set, and the camera block is the camera-specific part to drop on a server.

## 3. The player as a singleton

`World.Player` (World.cs:407) is one `PlayerState` (Simulation/Player/PlayerState.cs:15): `Faction` (int index), `FactionName`, `Money`, `SquadAi`, `BanditsLoot`, `Selection`, `Squad` (active squad), `Inspected`, `Pointed`, `InventoryShown`, `OpenContainer`/`OpenLoot`/`DoorTarget` and their walkers, `Held` (item on the mouse, hashed), `Towns`/`Camps`/`KnownFactions` (map knowledge), debug cheats. `PlayerSystem` is one system; `World.Research` (single `ResearchState`), `World.Buildings` ownership by faction index, `TradeSystem._session` and `DialogueSystem` hold one open trade and one conversation.

Counts: `Player.Faction` 244 hits in 95 files (Simulation about 212 in 79 files, Game about 32 in 16). `.IsPlayer` 288 hits in 109 files (Simulation about 200, Game about 85 mostly DevTools/Ui). `PlayerFaction` 114 hits in 44 files (data-level: `FactionRelations.PlayerFaction`, `PopulationData.PlayerFaction`). `Player.Selection` 45 hits in 28 files. By Simulation folder (Player.Faction): Locks ~31, Dialogue ~28, Ai ~23, Construction ~18, Production ~16, Kidnap ~14, Population ~13, Crime ~10, Factions 9, Saving ~9, Player ~8, rest 1-5 each.

Ten telling examples:
1. `FactionRelations` is a fixed n x n float array from the FACTION records; the player's row is "answered by the other side's table", `PlayerFaction` is one index (Data/Gameplay/FactionRelations.cs:13-67). The player faction is the record `204-gamedata.base` (`FactionData.PlayerId`, FactionData.cs:74). Per-player factions need growable/relation-defining rows.
2. Hostility to "the player": `AggroSystem` treats `c.IsPlayer || c.Faction == world.Player.Faction` as player (Aggro/AggroSystem.cs:327,1216,1628,1760,2166); `HostileToPlayer`/`FightsPlayer` in `CharacterSnapshot` (WorldSnapshot.cs:704,816).
3. Bounties, bail, jail, fines: `ArrestSystem.Bounties` reads/writes `world.Player.Money` and compares with `world.Player.Faction` (Crime/ArrestSystem.Bounties.cs:144-257,472-540); `BountyBook`, `CrimeSystem` pending crimes are "from the player's deeds".
4. Money: one purse `Player.Money`, used by trade, bail, dialogue effects (`DialogueSystem.Effects.cs:500`), squad dismissal (`SquadManagement.cs:306`), saved as CAMERA `player money` (SaveCapture.cs:157).
5. Recruiting: `DialogueSystem.Recruit.cs:54-146` joins the target to `world.Player.Squad` and sets `mc.Faction = world.Player.Faction`.
6. Squads: `SquadManagement.Mine` = `s.Faction == world.Player.Faction && s.PlatoonId < 0` (Factions/SquadManagement.cs:391), `Player.Squad` is the one active squad.
7. Bases/outposts: `ConstructionSystem` has 15 uses (e.g. `MayBeBuilt`, door/dismantle ownership, `AddTown(mean, world.Player.Faction)`, Construction/ConstructionSystem.cs:285-878); `Fixtures.PlayerOwnedIn`, `OwnedProperties(Player.Faction)` (WorldPublish.cs:290); BuildMode UI ownership (Game/Building/BuildMode.cs:1211).
8. Raids: `PopulationCampaigns.PlayerFactionOf` (:296) picks targets only among player towns with a player character within 1250 (docs/simulation.md:531): campaigns aim at "the" player.
9. Kidnapping/captives: `CaptiveSystem` (Kidnap/CaptiveSystem.cs:517,1207,1769-1818) tests `Player.Faction`, crop theft crimes name it; cage ownership `owner == Player.Faction`.
10. Selection is authority: orders with ids apply only if the ids are in `Player.Selection` (`PlayerSystem.WantsToGetUp`, Player/PlayerSystem.cs:159-175); orders with an empty id list resolve to the selection; commands carry no player identity.
Also: shops (`TradeSystem`, `Market`, `CharacterTrading` with 5 hits), research (`ResearchState`, Production/Construction), unique characters' "player flag" (`UniqueCharacters`), `PopulationSystem.RefreshStates` uses `Player.Faction` else `_data.PlayerFaction` (:208).

## 4. Time

- Sim tick 1/30 s of game time (`WorldSettings.TickSeconds`; `WorldSession` ctor rejects unequal clock/world ticks, WorldSession.cs:44). `SimulationClock` (Simulation/Session/SimulationClock.cs:15): speeds {0,1,2,5}, the two fast ones settings (1.5-4x, 5-20x); real dt capped at 0.05 s before the speed multiplier; budget `ceil(2*speed)` ticks a frame, excess dropped (`AchievedSpeed`). Control tick (input, camera) is 30 Hz real (`UserConfig.TickRate`, UserConfig.cs:336). Tick ahead: next ticks run on `Meitou.Tick` during the draw (docs/simulation.md:45-59; "a command lands a batch later").
- `World.PhysicsSpeed` (1,2,5) feeds ragdoll physics in real time, so ragdoll outcomes depend on game speed (not hashed, not saved; docs/simulation.md:61). `World.SpeedSteps` stretches sweep periods at 2x/5x (:28-35).
- Who changes time: `WorldSession.Tick` handles Speed1/2/3 keys (WorldSession.cs:581-583), HUD buttons (Game/PlayerInterface.Ui.cs:1397), `Session.Simulation.Pause()` from BuildMode (Game/Building/BuildMode.cs:200), photo mode (Host/Photo/PhotoMode.cs:550), the console (`AgentWorld.cs:275,1147,1178`). All are direct calls on the session, **not commands**.
- Assumes time can stop: modal UI sets `RequestedPause` (`UpdateMenuPause`, PlayerInterface.Ui.cs:1087); menus; the character editor world waits while `PlayerState.InCreation` (Discover skips it, PopulationSystem.cs:395; CONFIRM sets speed 1, CharacterEditorPanel.cs:535); `PauseOnLoad` (GameSaves.cs:573, default on); loading pause hold `LoadingHold` (SimulationClock.cs:116); warm-up and flights hold the simulation paused (docs/engine.md:62); the interface's own commands (selection, orders, inventory moves, trade buy/sell, dialogue choices, crafting, squads, build placement) are applied between ticks while paused through `World.ApplyPausedInterfaceCommands` (Simulation/World.Interface.cs:27-84), so shopping and inventory edit a frozen world; autosave counts only unpaused real time (GameSaves.cs:109); the agent `step` needs the clock paused (WorldSession.cs:289); `SettleAhead` before any save.
- Zone linger timers run on real time scaled by speed (`PopulationSystem.LingerSpeed`), and the original's would run out while paused (docs/simulation.md:25).

## 5. Commands

Mostly yes. `SimCommand` records with a `Tick` (Simulation/Commands.cs:12); `CommandQueue` (any thread enqueues; due ones taken in tick then queue order, :50-107); about 110 command types in 35 files. The UI sends everything through `PlayerInterface.Say` (Game/PlayerInterface.cs:779: plays a sound, then `World.Commands.Enqueue`); about 90 `Commands.Enqueue` call sites in 22 Game files (DevTools 7 files, scenarios, editors, `ModContext.Enqueue`). Orders are `OrderCommand` -> `PlayerOrders.Give` -> `OrderEntry` in `CharacterCold.OrderQueue`; `World.CanOrder` (Simulation/World.Orders.cs:20) is a pure read the UI uses to grey verbs.
Game classes also act or read outside commands:
- Direct writes: `Player.Pointed` (PointerView.cs:145, any thread, "not a command"); `GameSaves` sets `world.Player.Selection` after a load (GameSaves.cs:483-486); host sets `World.BenchFacingFix`, `PrisonPoseFix`, `BagSearchFix`, `TakeIntoBackpack`, `ActionLog`, `NearRadius`, `ViewPosition`, `Weather` (GameHost.cs:650-657); `ApplyGameplay` mutates systems' settings (GameSaves.cs:651-672); `GroundItems.Limit` (GroundItemSync.cs:43); `RequestedPause`/speed (section 4); `PopulationSystem.ZoneGate`; debug toggles (`StatsTo1000`, `AutoHeal`, `InstantMove`, `OnePunch` read by DebugMenu; set via commands in at least some cases).
- Direct reads of live World from UI (not snapshots): `Session.World.Tick` (about 150 uses), `Player.Faction`/`Money` (about 30), `World.CanTalk`, `VerbFactsOf` (ContextMenuWindow.cs:283,411), `ArrivalForget`, `Floaters`, `Systems` (OrdersPanel.cs:196). The UI otherwise reads snapshots (no `World.Characters/Fixtures/Squads/Buildings/Machines` reads in Game/Ui).
- Commands are not authenticated and carry no issuer: `ModContext.Enqueue` and `AgentChannel` use the same queue. Some commands carry a handle that only works in the issuer's session (`CharacterId` = slot + generation).
- Command ordering note: `CommandQueue.TakeDue` removes every due command; a consumer that does not apply one drops it (docs/simulation.md:114).

## 6. Snapshots

`World.Publish` (Simulation/WorldPublish.cs) fills a `WorldSnapshot` (record, `Tick` + character list; `Simulation/WorldSnapshot.cs:925`) and reuses `CharacterSnapshot` objects in a ring of four buffers (docs/simulation.md:37-43: stay valid until two more snapshots publish). Counts: `WorldSnapshot.cs` has 208 settable properties in total; `WorldSnapshot` about 106 `init` properties; `CharacterSnapshot` about 100 properties (identity, appearance, transform, animation, faction/squad/player/selection, body parts, skills and inventory only for the selected/inspected/pointed, orders, activity text, trader flag, kidnap chance, `HostileToPlayer`, `FightsPlayer`...).
It is built for one viewer: `Player.Selection`, `Pointed`, `Inspected`, `InventoryShown`, `OpenLoot`, `OpenContainer`, `Held`, `PlayerSquads`/`IndependentSquads`, `Trade`, `CharacterTrade`, `DialogueRequest`, `Towns`/`Camps`/`KnownFactions`, `OwnedTownBuildings`, `InspectedBuilding`, `Research`, `Machines`, `Buildings`, `NestBuildings`, `Outposts`, `MapSquads`, `GroundItems`, `Cages`, `Doors` (WorldPublish.cs:152-294, 403-654; WorldSnapshot.cs:938-1140). Detail work is limited to selected/pointed characters for cost (docs/simulation.md:97-102).
Live-world reads in the UI are small (section 5): the inventory, trade, stats, map and build windows read the snapshot plus a few helpers. Examples that do read the live world: `ContextMenuWindow` verb facts (:283,411), `FurnitureUse` ownership by `Session.World.Player.Faction` (34 `Session.World` uses), `TradeWindows`/`InventoryWindows`/`ProductionWindows` only for `Tick` when sending commands. The map reads `Player.Towns` via the snapshot (`WorldSnapshot.Towns`). Build mode reads snapshot buildings but uses `World.Player.Faction` (BuildMode.cs:1211). `GameHost.BuildingSync` (Host/WorldSync/BuildingSync.cs:128,272,538) reads `World.Player.Faction` to place navmesh obstacles and building visuals.
(inferred) The snapshot's single-viewer fields mean a multi-player server must build a per-player view or separate the shared world part from the personal part; the per-character shared part (about 100 properties) is large.

## 7. Saving

- Format: original-compatible save folder (docs/formats/save.md): `quick.save` (global, CAMERA record), `platoon/*.platoon` (one per squad), `zone/zone.X.Y.zone` (per visited zone), Meitou extras (`meitou-mods/<id>.dat`, `environment.json`, `meitou-weapon-blood.json`, `meitou seed`). `SaveCapture.PrepareBase` clones the loaded `SaveGame`, `Capture` writes over the clone so unmodelled keys pass through (docs/simulation.md:2135-2137). `SaveLoader.Load` (Simulation/Saving/SaveLoader.cs) makes characters before the first tick; state that must reach a tick goes through `World.Commands` (:2140).
- Where: `%LOCALAPPDATA%\kenshi\save\<name>\` (settings.cfg `User save location`), `continue=` in settings.cfg, install `save.log` (save.md:150-159). Autosave: `GameSaves.Autosave` (Game/Host/GameSaves.cs:99): real unpaused seconds, `Auto save time` x 60, rotating `autosave0..2`, index in `UserConfig.AutosaveIndex`. Capture is at a tick boundary after `SettleAhead` (:199); writing on a worker (`SaveWrite`); `SavesAvailable` needs the population (no sandbox).
- Tied to the single player: CAMERA `player money`, `pfaction name`, `formation`, squad toggles `bl heal ...`, selected-character handles, `pos/rot/zoom` camera view, `tracking` (save.md:296-310; SaveCapture.cs:157-163,2047); the player faction is found as the GAMESTATE_FACTION with a `known` list or id `204-gamedata.base` (`SaveGame.PlayerFaction`, Data/Save/SaveGame.cs:265); player platoons vs NPC platoons by faction; `BuildingSave.Write(game, world, playerFactionId, ...)` writes "player outposts" only for one faction (SaveCapture.cs:210); research in `quick.save`; `SaveLoader.Load` sets `Player.Faction/Money/FactionName/SquadAi/KnownFactions/Squad/Selection` (:157-175, 331-359); `world.Fixtures.SavedPlayer` (:189).
- Not restored exactly: orders/paths, animation, combat engagement, ground items, game speed; loaded hashes need not equal captured ones (docs/simulation.md:2148-2151). A snapshot-by-save join is therefore approximate (inferred).
- Import (`SaveImport`) builds a new world keeping only the player squads of another save.

## 8. Settings

Layout: `UserConfig` (Game/Host/UserConfig.cs, about 119 properties, `meitou.user.json`), `GameplaySettings` (Game/Settings/GameplaySettings.cs: 10 values read from the **install's settings.cfg** with the original's keys), `NewGameSettings` (7 difficulty floats stored in the save's CAMERA). Pages: `GamePages.cs`, `SettingsMenu.cs` (Fixes/Advanced switches reset together at SettingsMenu.cs:1533-1587). Original `settings.cfg` graphics values are not read.
How they reach the simulation (all pushed by the host, nothing in Simulation reads UserConfig):
- constructor options at world build: `StandardSystemOptions` fields (`Population`, `Ai`, `Captives`, `Construction`, `Production`, `Combat`, `Dialogue.Censored` callback, `AnimalsPickUp`), GameSaves.cs:677-723;
- live properties on systems by `ApplyGameplay` (GameSaves.cs:651-672) and `SettingsMenu` callbacks (:424-470): `PopulationSystem.Settings`, `AiSystem.Settings.TownAttacks`, `CombatSystem.StuckLimit`, `CaptiveSystem.Settings`;

- one static: `HeightmapRepair.Configure(install, FixGround)` at startup (Program.cs:83, Data/World/HeightmapRepair.cs:42), which changes terrain heights and so the navmesh hash.

Gameplay (affect rules/state; a server must decide them): Gameplay page `SquadSize`, `Population`, `RaidSize`, `RaidFrequency`, `TownAttacks`, `Dismemberment`, `HarpoonLimit`, `FastZoneHopping`; AutoSave and `AutoSaveMinutes` (server save policy); NewGameSettings (7: body hunger/death/damage, production, research, construction, nest density) which is already per save; Advanced switches `AttackSlots`, `LateDefences`, `KeepRoamers`, `OffscreenFights`, `OffscreenHealing`, `KeepWild`, `ResidentSchedule`, `UnloadedProduction`, `Decapitation`, `AdvancedRagdolls`, `SquadXp`, `OthersXp`, `AnimalsPickUp`, `CagesSpareOwn`, `FastSpeed`/`FastestSpeed`, `GroundItemLimit`, `FarTickPeriod` (engine); Fixes with sim effect `CampaignAncestorsOnce`, `FixGunnerFacing`, `FixPunchReach`, `FixAnimalMoves`, `FixBenchFacing`, `FixPrisonPose`, `FixBagSearch`, `TakeIntoBackpack`, `FixGround`. About 40 in total. Mixed: `PauseOnLoad`, `LoadingPause` (host timing), `TickAhead`, `SimThreads` (host performance; threads do not change results).
Client-only: graphics/look presets, audio and the `Fix*` audio/visual fixes (`FixDoorBreak`, `FixAmbienceSuffix`, `FixWindStop`, `FixLoadButton`, `FixHeadTurnBack`, `FixPartsInBuildings`, `FixRainInBuildings`), UI mode, camera options, `Censorship`, controls, bindings, hat/outline/head-turn looks, `TickRate` (control tick).
Note: these values live in the player's config and saved nowhere in the save, except the new-game floats and `meitou seed`; one process sets them for one world.

## 9. Mods

Data mods: `LoadOrder.FromInstall` (Data/LoadOrder.cs:48) and `GameDatabase.Load` read enabled files from `mods.cfg` in order; `GameDatabase.Files` lists the names; code mods' record edits go into `GameDatabase.CodeEdits` as fingerprints that are "the same on every machine and every language" (`ModDataChanges.Fingerprint`, Game/Mods/ModDataChanges.cs:95; docs/modding.md:172). `NavContentHash` (Simulation/Navigation/NavContentHash.cs:25) hashes file name + size + **write time** of data, map, level and collision files plus `CodeEdits` plus the DotRecast version; it is a local cache key (write times differ between machines) and not usable across machines.
Code mods: Game/Mods (`ModHost`, `ModContext`, `IMod`, `GameMods`), one `AssemblyLoadContext` per mod, one shared Harmony 3.0 (docs/modding.md:102-122), data phase `IModDataPhase.EditData` (:136-181), `IMod.Initialize` on the boot worker (:126). They reference `MeitouClient.dll` (the game exe, namespace `Meitou.Modding`) plus Simulation, Core, Data (docs/modding.md:28); `Meitou.Modding` stays in Game "until the mod contract moves to Simulation" (CLAUDE.md).
What stops mods on a window-less server: (a) the contract assembly is `MeitouClient.dll`, so a mod links the whole game; (b) `ModContext` registers Game-only UI services: `AddUi(IUiExtension)` (ModContext.cs:341), `AddCombatHitFeed`, `ArrangeFactionList` (faction window), `AddSettings` (settings page), `AddEquipmentSlot`/`AddMedicalMeter` (UI labels), `AddSkill` which calls `Game.Ui.StatsWindow.ModRoom` (:261), `AddDebugCommand`; (c) mod UI extensions get `PlayerInterface` (`GameMods.ConnectModUi`, GameMods.cs:140); (d) `ModContext.Data/Population` are the host's data: a server and its clients must hold identical merged data. Sim-side registrations (`AddSystem` at an anchor, dialogue codes, record types, wear rules, status effects, combat moves, item uses, job types) go through `SimulationExtensions` in Simulation and work without a window. Mod save data is `IModSaveData` per system in `meitou-mods/<id>.dat` (save.md:182-192). Mod rules: no World access outside the tick, outside input via `Enqueue`, randomness via `Rng.Hash` with the mod's purpose (modding.md:576-581). `mod-check` runs a mod on 3 headless runs and compares hashes (:583-600).
"Same data as the server" check, what exists: the load-order names (`GameDatabase.Files`, CAMERA `mods` list in saves), `CodeEdits` fingerprints, `environment.json` with code mod ids/versions/game version (save.md:189), `CodeModManifest.gameVersion`/`apiVersion` (`ModApi.Version`), `World.StateHash` (a diagnostic, platform-specific). Missing: a content hash of the merged `GameDatabase` or of each `.mod`/level file independent of write time, and a code-mod assembly hash.

## 10. Steam

Bound today: `SteamSession` (Game/Host/SteamSession.cs:34): loads the install's `steam_api64.dll` (Windows only), `SteamAPI_InitFlat`/`SteamAPI_Init`, `SteamAPI_Shutdown`, `ISteamApps::GetCurrentGameLanguage` (:107-143). `Core/Steam/SteamUgc.cs` (:118-124): Workshop only, through the flat API: `SteamAPI_RunCallbacks`, `ISteamUGC` GetNumSubscribedItems / GetSubscribedItems / GetItemState / DownloadItem / SubscribeItem, `ISteamUtils` IsAPICallCompleted / GetAPICallResult; plus `SteamLibrary`, `MacSteam`, `WorkshopSync`. App id 233860 (Kenshi's) only; no Steam binaries shipped. **No** networking, sockets, lobby, matchmaking, friends, user-identity or auth-ticket calls exist; the game never pumps callbacks in play (inferred from the grep of exports). Kenshi's own old API lacks the newer flat accessors, so the interface is fetched by version string through `ISteamClient` (SteamUgc.cs:29-31,278-282).

## 11. Determinism

Named sources of run-to-run difference:
- Path answers arrive at different ticks (`PathService` runs 2-4 threads, drops requests its character replaced; `SynchronousPaths` makes them tick-synchronous in tests, docs/simulation.md:118-122; StandardSystemOptions.SynchronousPaths).
- Population builds on a background thread (`PopulationSettings.Background`), navmesh zone readiness (`ZoneGate`, `RepathCommand` timing, `GateRegionsCommand`), zone collision gathered on a worker (`RagdollGeometry.Synchronous` removes it; **Observed** 2 of 48 runs differed under load, simulation.md:119-121).
- Tick ahead and frame/real-time inputs: commands land a batch later; `GameHours` from the host clock; `ViewPosition`/`NearRadius`/`FarTickPeriod` (headless 1); `PhysicsSpeed` (ragdoll physics real-time, differs between speeds); weather from the camera-driven scheduler on real frame times and particle zones; zone linger timers in real time x speed.
- Worker count: partitions are `threads*2` with min 16 (game 32) slots; "the result never depends on it" is the contract and golden scenarios must agree at 1/4/16 threads. Randomness is stateless `Rng.Hash(seed, entity, purpose, counter)`; state hash `StateHash` is ordered and normalises -0 (simulation.md:113-126).
Golden tests (tests/Meitou.Tests/Simulation/GoldenHashTests.cs:12-76): 22 scripted scenarios (wander, player, roaming, bodies, fight, duels, wander-parts, town-parts, first-aid, aggro, goal-fights, ranged, carry, crime, build, dialogue, ai, arrest, kidnap, production, wild, luckyren), each with 4-8 pinned `ulong` hashes, synchronous services, pins platform-specific (Windows pinned; Linux reproduces `production` and `build` only; Wine/Proton neither). Not covered by them: `GameHost` zone streaming, background population, async paths, weather, saving/loading round trips (QuickSaveTests check carried fields and repeatable loads only), real navmesh timing, tick ahead. `mod-check` covers mods on open terrain.

## What blocks a headless multi-player server today (largest change first)

1. **One player, one faction, everywhere.** `World.Player` (`PlayerState`), `PlayerSystem`, the single `Selection`/open trade/open conversation/held item, money, research, `Player.Faction` in about 95 files, `IsPlayer` in about 109, fixed n x n `FactionRelations` with `PlayerFaction` as a single row answered by others' tables. Touches Player/*, Factions/*, Crime/*, Dialogue/*, Trading/*, Construction/*, Production/*, Kidnap/*, Locks/*, Ai/*, Aggro/*, Population/* (campaigns, roaming), `PopulationData`, `FactionRelations`, `SquadManagement`, `UniqueCharacters`, snapshots.
2. **Player authority and identity in commands.** Orders are accepted if the ids are in the global `Selection`; commands carry no issuer; paused-interface commands, per-player trade/dialogue/inventory sessions are world-global. Touches Commands.cs, `OrderCommand`, `PlayerSystem`, `World.ApplyPausedInterfaceCommands`, `TradeSystem`, `DialogueSystem`, `PlayerInterface.Say`.
3. **Area activation is camera-centred and single-focus; zone and navmesh streaming live in `GameHost`.** `FocusCommand`, `PopulationSystem._focus`/`RefreshLoaded`, `ViewPosition`/`NearRadius`/`FarTickPeriod`, `ZoneGate`, `UpdateNav`/`SendRepath`/gate codes (GameHost.cs:1331-1534) and five `ZoneGate` assignment sites. A server needs these inside a Simulation-side host class driven by every player's characters, with no camera. Cost model for hundreds of players (zone union) is untested.
4. **No GPU-free host with a clock.** `WorldSession` mixes sim clocks with camera/input; `GameHost` mixes the world host with rendering; `BuildSystems`/`ApplyGameplay` hold the settings wiring; `--headless` still renders; the probe in Tools shows the shape but is single-threaded, synchronous and single-player. Time control (speed, pause, modal pause, pause on load, editor wait, `Step`) is direct session calls, not commands, and many features assume pausing (4).
5. **Weather is camera/renderer-driven** (`WorldWeather.Update`, camera region with 500-unit hysteresis, real frame times, particle-unit zones) but feeds `WeatherSystem`. Needs a game-clock-only scheduler (`WeatherWorld` already holds every region's schedule) and an authoritative effect-zone source.
6. **Snapshots are single-viewer.** `WorldPublish` mixes the shared world with one player's selection, windows, map knowledge, trade, dialogue, owned buildings; about 100 properties per character; ring-buffer reuse contract. Needs a shared state view plus per-player views or deltas.
7. **Saves and the player.** `SaveCapture`/`SaveLoader` read and write one player faction, CAMERA player fields, single camera/selection; save lives on the host (`GameSaves`: autosave, write worker, `SwapInSave` host-side clock/weather/camera). Loaded hash != captured hash, so a late-join by save is approximate.
8. **Settings are per-process client config.** `UserConfig`/settings.cfg pushed by `GameSaves.ApplyGameplay`, `SettingsMenu`, a static `HeightmapRepair`, the shared mutable `PopulationData.BodyOptions`; the gameplay subset (about 40) must become server data, with the client-only remainder kept local.
9. **Code mods' contract is `MeitouClient.dll` with Game-only UI services.** Move `Meitou.Modding` to a window-less assembly, make UI registrations optional or client-side, split sim-side from UI-side registrations; add a content hash of merged data and code mod assemblies for the join check.
10. **Determinism sources not covered by tests**: async paths, background population, navmesh readiness, tick ahead, `PhysicsSpeed`, real-time linger timers. They matter if the server and clients both simulate or the server replays; they matter less if clients render only snapshots.
11. **Steam**: no networking, lobby, identity or auth bindings; Windows-only library load; only app id 233860.
